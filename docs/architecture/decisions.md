# Design decisions

Short architecture decision records, reconstructed from the plan documents in
[`docs/`](..) and the code that implements them. Each is current unless
marked otherwise. Dates are given where the source states one.

---

## ADR-01 — The server is authoritative; clients derive no rules

**Context.** The original Žolíky clients each re-implemented enough rules to
decide what to show (enabled buttons, card values, contract names), and drifted
from the engine ([`architecture.md`](../architecture.md) §6).

**Decision.** Every rule-derived fact is computed once, in the module, and
shipped. Offers carry enabled/disabled state, reasons, costs (`Facts`) and
remedies; the view carries pre-resolved facts.

**Consequences.** Adding a game needs no client rule code. Any client logic
that has to compute a rule is treated as a bug. The wire is larger (full offer
lists with disabled entries every broadcast).

## ADR-02 — One module interface, falsified against unlike games

**Context.** An interface designed against one game fits one game
([`extensibility-plan.md`](../extensibility-plan.md)).

**Decision.** `module.GameModule` (six methods) with opaque JSON `State`,
designed alongside Prší and then deliberately tested against Canasta, Hold'em
and Blackjack ([`one-architecture-plan.md`](../one-architecture-plan.md)).
Extra capabilities are optional interfaces discovered by type assertion.

**Consequences.** The runtime cannot peek at state (no 30-field mapping to keep
in sync). Each new kind of game has bent the interface in a named, documented
place (`ParamSpec`, winners as a list, `Seat`, `Composite`, `from_meld`).

## ADR-03 — Offers are the whole input vocabulary, including drag-and-drop

**Decision.** `LegalActions` returns every offer, disabled ones included with a
stable `WhyNot` code. An offer's `Source`/`Target` selectors say which cards go
where, so drop targets are a filter over offers. Bots, hints, the conformance
driver and MCP agents all act only through offers.

**Consequences.** "Greyed out, and here is why" is free for every game; a game
playable by the offer-only conformance driver is playable by the generic UI.

## ADR-04 — Keys, never sentences

**Decision.** The server sends message keys and params; all wording lives in
client locale bundles. A golden file, `serverKeys.json`, lists every key the
server can emit, generated by `cmd/dump-keys`; tests on both sides enforce it.
Keys must be static literals so the scanner can find them.

**Consequences.** A new language is a client-only change (24 bundles today).
Every new server key costs 24 translations and a regenerated golden file.

## ADR-05 — Refusals point at written rules

**Context.** A refusal code names a class of refusal, which does not explain a
specific one; per-code explanation text would be a second, unversioned copy of
the rules.

**Decision.** Modules write their rules (`Rules(cfg)`, resolved for the actual
table) and map refusal codes to rule ids (`ExplainRefusal`). Offers and error
frames carry `ruleIds`; the client links to the sentence on the rules screen.
Codes a package can emit are read from its source and must all be mapped.

**Consequences.** Explanations always match the table's options and locale.
Adding a refusal means adding (or pointing at) a written rule.

## ADR-06 — House rules are declared options

**Decision.** A rule that tables play differently becomes an `OptionSpec` in the
module descriptor, with a default equal to the existing behaviour, validated by
the runtime at creation. Not a constant, not a fork.

**Consequences.** Old matches keep their behaviour; the rules text and the
setup form pick the option up automatically.

## ADR-07 — Bots belong to the runtime

**Context.** Only Žolíky had opponents, because its AI lived in its runtime
(Phase 6 of the one-architecture plan).

**Decision.** The runtime drives a bot for any seat that needs one, through the
same write path as a human. A module supplies a `Bot` or gets the offer-reading
default. Bot randomness is seeded from the match seed and seat, never the wall
clock.

**Consequences.** Every new game has an opponent on day one. Bot mistakes are
reproducible. Undo offers needed special handling so a pure-function bot cannot
oscillate.

## ADR-08 — Embedded kdb in production; Mongo kept behind a flag

**Context.** A card game on a 1–2 GB host does not need a database server; an
acknowledged write should survive power loss ([`kdb-port.md`](../kdb-port.md)).

**Decision.** One repository layer, two engines, chosen at start by
`FEATURE_FLAG_DB_ENGINE`. Production runs kdb embedded in the process (fsync per
commit, single instance). Mongo (+ Redis for fan-out) remains supported and is
the code default when the flag is unset.

**Consequences.** One process, one container, no Redis. Uniqueness and CAS are
enforced in-process. Horizontal scaling is a Mongo-only story. The binary links
kdb, which is AGPL-3.0, so the combined work is AGPL and the running app offers
its source.

## ADR-09 — Moves stored once; the board lives in memory

**Context.** Rewriting the whole match document every move dominated storage
and write cost.

**Decision.** A move is appended once; the board is held in memory and
snapshotted at the deal, every ~100 moves, at widely spaced round boundaries and
at the end. A match not in memory is rebuilt from its newest snapshot plus later
moves, which `Apply`'s determinism makes exact. All access goes through one
lock per match.

**Consequences.** Readers must use `Manager.Current`, not the repository, for a
live board. Old stores need `cmd/migrate-match-log`. Multi-instance deployments
must detect foreign writes (done when Redis is on).

## ADR-10 — kdb namespaces per match and per user

**Decision.** Each match is its own namespace (`m/<id>`), each user has
`u/<id>` and a cloud-written `u/<id>/ro`, and devices hand finished games up
through `node/<id>/outbox`. A namespace is kdb's unit of replication and
authorisation.

**Consequences.** "Sync this match to the four people playing it" is
expressible. A node-local `matches` index is written in the same
cross-namespace transaction so scans still work.

## ADR-11 — Plain JSON on kdb, BSON only on Mongo

Decided and implemented 2026-10-15 ([`kdb-plain-json-storage-plan.md`](../kdb-plain-json-storage-plan.md)).
kdb documents are plain JSON with `bson` tag names; reads accept the old
extended JSON as well, with `KDB_DOC_WRITE_FORMAT` as a rollout switch.

## ADR-12 — One image is the deployment

Decided and cut over 2026-09-07 ([`docker-deploy-plan.md`](../docker-deploy-plan.md)).

**Decision.** Build one image on the developer machine (Go server with the web
bundle embedded), ship it with `docker save | ssh docker load`, run it from one
compose file. No source, toolchain or kdb checkout on the host; host nginx kept.

**Consequences.** API and web client can never be different commits. Rollback is
the previous tag. The database volume is named explicitly and nothing in the
deploy path may remove it.

## ADR-13 — The operator console is absent from the public listener

**Decision.** `/admin` is registered on a separate router served on a second,
loopback-bound listener, reached by SSH tunnel; it does not start unless
credentials are configured ([`logging-and-reporting-plan.md`](../logging-and-reporting-plan.md)).

**Consequences.** The public vhost can stay a single catch-all proxy without
exposing the console. Operators need SSH access.

## ADR-14 — Backpressure declines arrivals, never evicts

**Decision.** The admission gate refuses new connections and matches past a
connection, memory or CPU watermark (503 with `Retry-After`), always admits
reconnects, and never drops an established player. `GOMEMLIMIT` sits below the
memory watermark so the collector runs before anyone is refused
([`memory.md`](../memory.md)).

## ADR-15 — Trained models ship in the binary; AI is its own skill

**Decision.** Networks are trained in Python against the real Go engine
(`cmd/gameenv`, never a reimplementation), exported as `ZLNET1`, and embedded in
the server. They play seats at skill `ai`, which sits above Hard but outside the
Easy/Medium/Hard ladder. An operator switch per game decides whether AI seats use
the model; a game with no stored choice is switched on if its model fits.

**Consequences.** A rollback restores the matching models. Hard stays a
measured, hand-written baseline. A model that cannot play falls back to the
heuristic, never to an arbitrary offer.

## ADR-16 — Govern bot compute by leases; change engines only at safe points

Decided 2026-09-29 ([`bot-compute-gating-plan.md`](../bot-compute-gating-plan.md)).
Expensive bot classes need a lease from a CPU budget scaled by the resource
monitor; without one a seat plays the cheaper engine. Downgrades happen at a
turn boundary, upgrades at a round boundary. Shipped in observe mode first.

## ADR-17 — No Expert level

An Expert bot was built and measured with `ai/sim`; it could not be shown to
beat Hard, so its ideas moved into Hard and the label did not ship
([`module/skill.go`](../../server/internal/module/skill.go)).

## ADR-18 — Skins change colour and decoration, never size

Drop targets are hit-tested by measured size, and every test and measurement
must be identical under every skin, so a skin may not change any size,
typography included ([`src/skins/types.ts`](../../client-react-native/src/skins/types.ts)).

## ADR-19 — AI agents are seated as players

Decided for Phase 1 of [`mcp-agent-seats-plan.md`](../mcp-agent-seats-plan.md).
An MCP client registers with an ordinary (even guest) token and plays through
tools that call the same `HandleAction`. It is flagged `IsAgent` and subject to
the same presence rules; the agent registry is in memory.

## ADR-20 — Phones run the same server

**Decision.** The phone and Mac apps embed the real runtime (gomobile) and host
offline tables over loopback, Wi-Fi or Bluetooth; the cloud relays remote
guests' sealed bytes without reading them ([`drop-handling-and-hybrid-plan.md`](../drop-handling-and-hybrid-plan.md)).
Games whose deal must stay secret from the device (`ServerDealt`) are never
hosted or synced on a device. Finished offline games go to the cloud only with
each player's consent, and are verified by replay before they are recorded.

## ADR-21 — Guests are first-class and claimable

**Decision.** Anyone can play as a guest; the guest's history is kept against a
durable guest id and claimed onto an account at sign-in. Possession of a guest
is proved by a stateless key (id + MAC), not by the public guest id. Guest access
tokens live 7 days because a guest has no other way back in.

## ADR-22 — Passwordless sign-in

Email sign-in uses one-time codes; there is no password to reset or leak.
Google, Apple and Microsoft are one generic OIDC implementation with provider
quirks as configuration. Username/password remains only for the SSH client.
